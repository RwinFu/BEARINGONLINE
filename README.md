# دفتر درخواست‌های برینگ آنلاین

پنل فارسی استاتیک برای GitHub Pages؛ داده‌های مشتریان مستقیماً از مرورگر در یک مخزن خصوصی جداگانه در GitHub ذخیره می‌شوند. هیچ بک‌اند یا سرویس دیگری برای نسخه جدید لازم نیست. هر درخواست یک فایل JSON در مسیر `requests/` مخزن داده است و پیش‌فاکتور و پیگیری‌ها همراه همان درخواست ذخیره می‌شوند.

## راه‌اندازی

1. یک مخزن **خصوصی و جدا از مخزن برنامه** برای داده‌ها ایجاد و با یک README اولیه مقداردهی کنید تا شاخه پیش‌فرض داشته باشد. هیچ‌وقت آن را عمومی نکنید و GitHub Pages را برای مخزن داده فعال نکنید. به همکارتان فقط دسترسی لازم به همین مخزن بدهید. مخزن برنامه `RwinFu/BEARINGONLINE` به‌عنوان مخزن داده پذیرفته نمی‌شود.
2. در تنظیمات مخزن برنامه، Pages را با منبع **GitHub Actions** فعال کنید. پس از ادغام کد در `main`، گردش کار `.github/workflows/pages.yml` فقط پوشه `public` را منتشر می‌کند؛ همچنین می‌توان آن را دستی اجرا کرد. آدرس Pages را در تنظیمات Pages یا اجرای workflow ببینید. انتشار Pages از مخزن خصوصی به نوع حساب و امکانات GitHub وابسته است؛ در صورت پشتیبانی نشدن، کد عمومی پنل را می‌توان جداگانه منتشر کرد، ولی مخزن داده باید خصوصی بماند. اطلاعات مشتریان را هرگز در مخزن عمومی یا پوشه انتشار قرار ندهید.
3. هر کاربر شخصاً یک fine-grained personal access token در تنظیمات GitHub خودش ایجاد کند: فقط مخزن خصوصی داده‌ها انتخاب شود، مجوز **Contents: Read and write** و دسترسی metadata پیش‌فرض داده شود و تاریخ انقضا مشخص شود. اعضا باید دسترسی نوشتن به مخزن داشته باشند. از حساب‌های جداگانه استفاده کنید. هر کاربر در صفحه منتشرشده نام مخزن به شکل `owner/repository` و دسترسی شخصی خودش را وارد می‌کند. آن را برای هیچ‌کس ارسال نکنید و در فایل یا مخزن ننویسید.
4. صفحه فقط روی آدرس Pages مورد اعتماد و با HTTPS باز شود. کلید صرفاً در حافظه صفحه می‌ماند و با خروج، بازخوانی یا بستن صفحه پاک می‌شود. چون برنامه در مرورگر اجرا می‌شود، کد مخرب مرورگر، افزونه‌ها یا تغییر غیرمجاز کد منتشرشده می‌توانند به دسترسی کاربر برسند؛ تنها کد مورد اعتماد را منتشر کنید. در صورت افشا، دسترسی را فوراً در GitHub لغو کنید.

## عملکرد و محدودیت‌ها

- ثبت درخواست با اطلاعات دستی یا فقط فایل PDF/JPG/PNG تا ۵ مگابایت، ویرایش، پیگیری، جست‌وجو، فیلتر و خروجی JSON فراهم است. اطلاعات فایل خودکار استخراج نمی‌شوند. فایل‌ها به صورت Base64 در JSON ذخیره می‌شوند و خروجی نیز شامل آن‌هاست.
- تغییر هر درخواست یک commit در شاخه پیش‌فرض مخزن داده ایجاد می‌کند. اگر همان درخواست هم‌زمان تغییر کند، ذخیره دوم رد می‌شود؛ متن را کپی کنید، فهرست را به‌روز کنید و مجدداً وارد کنید. پس از خطا دکمه به‌روزرسانی در صفحه اصلی است. تاریخچه Git نسخه‌های قبلی، حتی اطلاعات و فایل‌های جایگزین‌شده را نگه می‌دارد؛ حذف اطلاعات از تاریخچه نیاز به اقدام جداگانه دارد.
- GitHub محدودیت حجم، تعداد درخواست API و سرعت دارد و این روش برای حجم زیاد داده یا کاربران زیاد مناسب نیست. تعداد زیادی فایل یا پیش‌فاکتور بزرگ باعث کندی و رشد مخزن می‌شود. مخزن داده باید شاخه پیش‌فرض قابل نوشتن داشته باشد؛ قوانین محافظت شاخه ممکن است ذخیره را مسدود کنند. خصوصی بودن مخزن قبل از اتصال و هر ذخیره بررسی می‌شود، اما مسئولیت حفظ تنظیم خصوصی و مدیریت دسترسی‌ها با مالک است.
- دکمه خروجی JSON از اطلاعات بارگذاری‌شده نسخه محلی می‌سازد و آن را باید امن نگهداری کرد. پشتیبان‌گیری و بازیابی خودکار وجود ندارد. ورود درخواست‌های سایت خودکار نیست.
- داده‌های SQLite نسخه قبلی خودکار منتقل نمی‌شوند. فایل `data/requests.sqlite` مربوط به نسخه قبلی روی همان سرور است و در GitHub ثبت نشده است. پیش از کنار گذاشتن آن، از آن به‌شکل امن نسخه پشتیبان بگیرید. `server.js` صرفاً برای استفاده از نسخه قدیمی داده‌ها نگهداری شده؛ پنل جدید به API آن وصل نمی‌شود.
- تاریخ پیگیری میلادی وارد و شمسی نمایش داده می‌شود. قیمت و نرخ دلار به تومان هستند.

## آزمایش محلی ظاهر

با `python3 -m http.server 3000 --directory public` پوشه استاتیک را اجرا کنید. اتصال واقعی به GitHub نیاز به مخزن خصوصی و دسترسی جداگانه دارد؛ از اطلاعات واقعی در محیط آزمایشی ناامن استفاده نکنید.
